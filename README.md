# Agent UML CLI

[![CI](https://github.com/vladbagmet/uml_cli/actions/workflows/ci.yml/badge.svg)](https://github.com/vladbagmet/uml_cli/actions/workflows/ci.yml)
[![License: MIT](https://img.shields.io/badge/license-MIT-blue.svg)](LICENSE)
[![Node.js >= 22](https://img.shields.io/badge/node-%3E%3D22-brightgreen.svg)](package.json)

`uml` turns a JSON model into a clean UML 2.5.1 diagram, as SVG or PNG. It draws
all 14 diagram kinds, from class and sequence to timing and profile diagrams,
and it is built for agents as users: every model is checked against a published
JSON Schema, every error is one JSON object that lists every problem with a fix
where one is clear, and every drawing is checked for layout defects before it is
written. Models also export to PlantUML and Mermaid text and import back.
Rendering is offline and needs no server, API key, browser, Graphviz or global
installation.

![Four diagrams drawn by uml: a class diagram, a sequence diagram, a state machine and a deployment diagram](docs/images/hero.png)

Version 1.0.0. Changes: [CHANGELOG.md](CHANGELOG.md).

## Quick start

You need Node.js 22 or later.

```sh
git clone https://github.com/vladbagmet/uml_cli.git
cd uml_cli
npm ci && npm run build
alias uml="node $PWD/dist/cli.js"

uml example class > model.json        # a minimal valid model to start from
uml validate model.json               # {"valid":true,"kind":"class","version":2}
uml render model.json -o diagram.svg  # or -o diagram.png
uml render examples/class/ordering.json -o ordering.png
```

Eleven kinds work right away. Sequence, timing and activity diagrams need the
PlantUML renderer, which one command downloads ([below](#plantuml-renderer-sequence-timing-activity)).

## Install

Requires Node.js 22 or later and npm.

From a source checkout:

```sh
npm ci
npm run build              # dist/cli.js; run it as node dist/cli.js or npm exec --offline -- uml
npm test                   # unit tests, no Java needed
```

From a release: every [GitHub Release](https://github.com/vladbagmet/uml_cli/releases)
has the npm tarball and a `SHA256SUMS.txt` attached. The package is not on the
npm registry; install the tarball into your project:

```sh
version=1.1.0              # the release you want
base=https://github.com/vladbagmet/uml_cli/releases/download/v$version
curl -LO "$base/agent-uml-cli-$version.tgz" -LO "$base/SHA256SUMS.txt"
shasum -a 256 -c SHA256SUMS.txt
npm install "./agent-uml-cli-$version.tgz"
npx uml --help             # or npm exec --offline -- uml --help
```

A tarball you build yourself with `npm pack` in a checkout installs the same
way. How releases are made: [docs/releasing.md](docs/releasing.md).

### PlantUML renderer (sequence, timing, activity)

Eleven kinds use the built-in engine and need nothing else. Sequence, timing and
activity diagrams (and class diagrams with `--backend plantuml`) are drawn by a
pinned PlantUML running on a private Java runtime, which a setup script downloads
once:

```sh
npm run setup:renderer                                     # in a source checkout
node node_modules/agent-uml-cli/scripts/setup-renderer.mjs # in a project that installed the package
```

It downloads the MIT-licensed build of PlantUML 1.2025.10 and the Eclipse
Temurin JRE 21.0.11+10 (about 60 MiB in total, about 215 MiB on disk) from their
official GitHub releases, checks each against a pinned SHA-256, and unpacks them
into the package's own `.tools/` directory. It runs on macOS and Linux, arm64
and x64 (Linux needs glibc and `tar`), changes nothing system-wide, and repairs
an interrupted or broken install when run again. After that, rendering is
offline. `uml --help` prints the exact setup command for the installed copy.
The runtime lives inside the installed package, so after npm replaces the
package (an upgrade, a clean install) run the setup again; `RENDERER_MISSING`
says so. To use a separately managed, trusted Java and PlantUML jar instead, set
both `UML_JAVA` and `PLANTUML_JAR`.

### Fonts

Nothing to install. The Inter font (SIL Open Font License) ships with the
package: the built-in engine measures text with it, every SVG embeds the subset
it uses, PNG output uses it, and the setup script installs it into the private
Java runtime so PlantUML measures with the same font. Glyphs Inter lacks (CJK,
emoji) come from the viewer's fonts in SVG.

## Usage

```sh
uml example class > model.json                # a minimal valid model to start from
uml schema class                              # JSON Schema of a kind: every property, allowed values
uml validate model.json                       # {"valid":true,"kind":"class","version":2}
uml render model.json -o diagram.svg          # or .png (2x by default)
cat model.json | uml render - -o diagram.png --scale 3
uml render model.json -o diagram.svg --backend plantuml
uml render model.json -o diagram.svg --strict # fail instead of warning on layout defects
uml kinds                                     # the 14 kinds, their backends and formats, as JSON
uml render --help                             # every command has its own help
```

The output format follows the `-o` extension unless `--format svg|png` is given;
`--scale 1` to `4` sets the PNG pixel density. The output is replaced
atomically, only after a successful render, and its parent directory must
exist. An existing device or pipe (`-o /dev/null --format svg`,
`-o /dev/stdout`) is written directly. Successful runs print nothing on stdout,
except `validate`, `example`, `kinds`, `schema`, and `export` and `import`
without `-o`.

### Writing models

Start from `uml example <kind>`, look properties up in `uml schema <kind>`, then
run `uml validate`; when it fails, the error lists every problem with a
corrected value where one is clear (see [Errors](#errors)). Every document is a
JSON object with a `kind`, an optional `title` (drawn as the frame heading) and
the kind's vocabulary. Rules shared by all kinds:

- IDs: unique ASCII identifiers `[A-Za-z][A-Za-z0-9_-]{0,63}`, one namespace per
  document. Relationships use IDs, never names. IDs are never drawn.
- Display text is Unicode shown literally, never parsed as markup or code: single
  line, no control characters, bidi overrides/isolates, unpaired surrogates or
  U+FFFE/U+FFFF; nonblank. Names 1 to 100 code points, other text 1 to 180, notes
  1 to 1000 (wrapped). Quotes, braces, HTML-like syntax and repeated spaces stay literal.
- Input is UTF-8 JSON of at most 256 KiB. Unknown properties are errors.
- v1 documents (the 0.1 format: `classes` + `relationships`, no `kind`, see
  [`schema/model-v1.schema.json`](schema/model-v1.schema.json) and
  [`examples/v1/`](examples/v1/)) keep working as class diagrams.

The guide to each kind, with the direction of every relationship and a minimal
model, is [docs/writing-models.md](docs/writing-models.md). Each kind's notation
checklist in [docs/kinds/](docs/kinds/README.md) lists every supported construct,
its rules and its known limitations.

### Export and import: PlantUML and Mermaid

Models export to the text formats people already share, and import back:

```sh
uml export model.json --to plantuml            # every kind
uml export model.json --to mermaid -o d.mmd    # class, sequence, state machine, activity, use case
uml import diagram.puml -o model.json          # class, sequence, state machine, use case, activity
cat diagram.mmd | uml import - --from mermaid  # class, sequence, state machine
```

The text is plain and readable (your IDs become the aliases) and, in the Mermaid
case, renders natively on GitHub, GitLab and most wikis. Anything a format
cannot express is reported as an `EXPORT_LOSSY` warning with its JSON path; a
kind Mermaid cannot draw fails with `UNSUPPORTED_EXPORT`, naming the formats
that work. Import reads the part of each syntax that maps onto the model and
reports every other line, with its line number, instead of guessing; the result
is validated like `uml validate`. `uml kinds` lists what each kind exports to
and imports from. Mapping tables and lossy cases:
[docs/formats.md](docs/formats.md).

## Errors

Errors are one JSON object on stderr; no output file is written or changed.

```json
{"error":{"code":"SCHEMA_INVALID","message":"2 problems; fix all of them (each is also listed in \"diagnostics\" with its path): (1) Unknown property \"methods\" in /elements/0 (type \"class\"); did you mean \"operations\". Allowed properties: id, type, name, stereotypes, attributes, operations, abstract (2) /relationships/0/type is \"inheritance\", which is not a known type; did you mean \"generalization\". Allowed values: \"generalization\", \"realization\", ...","path":"/elements/0/methods","diagnostics":[{"code":"SCHEMA_INVALID","path":"/elements/0/methods","message":"...","details":{"rule":"additionalProperties","property":"methods","allowed":["id","type","name","stereotypes","attributes","operations","abstract"],"suggestion":"operations"}},{"code":"SCHEMA_INVALID","path":"/relationships/0/type","message":"...","details":{"rule":"discriminator","allowed":["generalization","realization","association","aggregation","composition","dependency","containment"],"value":"inheritance","suggestion":"generalization"}}]}}
```

Written so an agent can fix a model in one round:

- `diagnostics` lists every problem, one entry per problem, in document order,
  each with a JSON Pointer `path`; `message` summarises all of them; `code` and
  `path` are the first one's.
- Unknown properties list the allowed ones and the nearest match (typos and names
  from other tools: `methods` -> `operations`, `label` -> `name`, `source`/`target`
  -> `from`/`to`, `participants` -> `lifelines`, `tags` -> `attributes`, ...).
  Wrong `type` (or other enumerated) values list the allowed values and the nearest
  one (`inheritance` -> `generalization`, `"type": "alt"` -> a fragment with
  `"operator": "alt"`). Formats are described in words with examples, never as a
  regular expression (`"0..n"` -> `"0..*"`, `"engine.tank"` -> `"engine-tank"`).
- `details.suggestion` holds the corrected value or property name where it is
  clear; `details.swap` the corrected `from`/`to` when a relationship looks
  reversed. Problems that appear once those corrections are made are reported in
  the same error, marked `details.afterFixes`.
- Unknown kinds, IDs and commands get "did you mean"; a reference by name points
  at the ID; keywords written with guillemets and guards or constraints written
  with their brackets are rejected with the bare text (the diagram adds them).
- `INVALID_JSON` gives the line, column and a hint (trailing comma, comment,
  single quotes); file errors name the path and the reason (`errno`).
- Import errors list every unreadable line as `UNSUPPORTED_SYNTAX` or
  `MALFORMED_LINE` with path `/lines/<n>`; a model that reads but breaks a rule
  fails with `IMPORT_INVALID`, the model in `details.model`.
- `RENDERER_MISSING` names the setup command for the installed copy in
  `details.setup`.

Exit codes: `0` success (possibly with warnings), `2` usage or input
validation, `3` renderer, `4` file I/O, `5` layout check failed under `--strict`,
`130`/`143` interrupted by SIGINT/SIGTERM. Codes include `USAGE`, `INVALID_JSON`,
`INVALID_ENCODING`, `INPUT_TOO_LARGE`, `INPUT_READ_FAILED`, `SCHEMA_INVALID`,
`INVALID_TEXT`, `UNKNOWN_KIND`, `DUPLICATE_ID`, `MISSING_REFERENCE`, kind-specific
rule codes (see `docs/kinds/<kind>.md`), `UNSUPPORTED_BACKEND`,
`UNSUPPORTED_EXPORT`, `UNSUPPORTED_IMPORT`, `UNSUPPORTED_SYNTAX`,
`MALFORMED_LINE`, `IMPORT_INVALID`, `RENDERER_MISSING`, `RENDER_FAILED`,
`RENDER_TIMEOUT`, `RENDER_OUTPUT_LIMIT`, `RENDER_INTERRUPTED`,
`RASTERIZE_FAILED`, `OUTPUT_WRITE_FAILED`, `LAYOUT_QUALITY`.

### Warnings and `--strict`

Every render runs the same layout checks the test suite uses (a few
milliseconds). When the drawing fails one, the file is still written and the
exit code is 0, but stderr carries one JSON object with one warning per failed
check:

```json
{"warnings":[{"code":"LAYOUT_QUALITY","gate":"label-edge-crossing","message":"Layout check \"label-edge-crossing\" found 1 problem: label \"places\" crosses edge r3","count":1,"problems":["label \"places\" crosses edge r3"],"advice":"A line runs through a label. Shorter labels or fewer crossing relationships usually help."}]}
```

`problems` holds up to five of the check's findings; `advice` says what usually
helps, in terms of the model, or that the problem is a renderer defect the model
cannot avoid. With `--strict` the same finding is an error instead: exit code 5,
code `LAYOUT_QUALITY`, the warnings in `details.warnings`, and no output is
written or changed. `uml export` reports constructs the target format cannot
express the same way, as `{"warnings":[{"code":"EXPORT_LOSSY","path","message"}]}`.
Some dense layouts still produce warnings; the ones the test suite tolerates for
now are listed with their review findings in `test/known-gate-failures.mjs`.

## Limits and known limitations

- **Input.** UTF-8 JSON, at most 256 KiB. Names 1 to 100 code points, other text
  1 to 180, notes 1 to 1000. Rendered SVG is capped at 8 MiB; PlantUML gets a 20 s
  timeout and a 256 MiB heap.
- **Emoji in PNG.** No emoji font is bundled, so PNG output draws an emoji as a
  box ("□"); the SVG keeps the emoji for the viewer's fonts. CJK and other scripts
  Inter lacks come from system fonts in PNG
  ([decision 0003](docs/decisions/0003-png-text.md)).
- **Activity swimlanes.** PlantUML draws the branches of a decision or fork side
  by side in every swimlane they use, so structures that would cross are rejected
  rather than drawn badly (`DECISION_SPANS_PARTITIONS`,
  `BRANCHES_SHARE_PARTITIONS`, `UNSTRUCTURED_FLOW`; each error says what to write
  instead).
- **Very large diagrams** get wide or tall rather than crowded, and dense ones
  keep long routes and can produce layout warnings. Splitting a model into
  several diagrams reads better. Timing diagrams too dense for a 3200 px axis are
  rejected with `TIMELINE_TOO_DENSE` and the room they need. Inline interactions
  in an interaction overview have at most 6 lifelines and 12 messages.
- **Ports with many connectors.** A port takes up to three connectors on separate
  lines; with more, the connectors share a trunk next to it.
- **Two backends, one look.** Colors, sizes and the font match, but PlantUML
  kinds draw glyphs through Java, so they can differ slightly from own-engine
  kinds. PlantUML output is checked by the same gates on a best-effort reading of
  its SVG.
- **Platforms.** The renderer setup supports macOS and Linux (glibc) on arm64 and
  x64. Other systems are not tested.

## Safety

- **Validation first.** The whole document is validated before any renderer is
  discovered or started.
- **Own engine SVG** is written by an escaping writer that only knows presentation
  elements: no scripts, links, `foreignObject`, images, event handlers or external
  references. The only `url(...)` is the embedded font subset (`data:` URL).
- **PlantUML** gets private aliases and UTF-16-unit-encoded display text, so input
  cannot become source lines, includes, links or markup. Java runs without a shell,
  with PlantUML's SECURE profile, 256 MiB heap, 20 s timeout, 8 MiB SVG and 64 KiB
  diagnostics limits; Java option injection variables are removed.
- **Deterministic.** Repeated renders are byte-identical in the same environment.

## How it works

A model is parsed and validated (size, JSON syntax, the kind's schema, text
rules, the kind's semantic rules), then drawn by its kind's backend: eleven
kinds by the own engine (elkjs 0.11.1 layout, text measured with HarfBuzz and
the pinned Inter font within 0.2 % of Chrome's own measurement, hand-written
SVG with an embedded font subset), and
sequence, timing and activity by PlantUML's dedicated engines, post-processed to
UML notation. Both share one theme. Every drawing then goes through geometry
checks (no overlaps, no label on a line, arrowheads present, text inside its box
and more); own-engine SVGs carry `data-uml-*` attributes so those checks are
exact. PNG output is rasterized with resvg. The details, with the reasons behind
each choice, are in [docs/architecture.md](docs/architecture.md) and
[docs/decisions/](docs/decisions/).

## Development

```sh
npm run build              # compile src/ to dist/
```
