# Contributing

Thank you for helping. Bug reports, small fixes, new examples, notation
improvements and whole new diagram features are all welcome. This page tells you
how to get set up and what a pull request needs so it can be merged quickly.

If you work with a coding agent, point it at [AGENTS.md](AGENTS.md): it has the
same rules in a form an agent can follow.

## Set up

You need Node.js 22 or later. Java is optional: only the PlantUML kinds
(sequence, timing, activity) need it, and the setup script downloads a private
copy.

```sh
git clone https://github.com/vladbagmet/diagramc.git
cd diagramc
npm ci
npm run build
npm test                    # unit tests, no Java needed
npm run setup:renderer      # once: pinned PlantUML and Java runtime into .tools/
npm run test:integration    # tests that run the real PlantUML renderer
```

Try the CLI from your checkout with `node dist/cli.js render examples/class/ordering.json -o /tmp/ordering.svg`.

## Commands

| Command | What it does |
|---|---|
| `npm run build` | Compile TypeScript from `src/` to `dist/` |
| `npm run typecheck` | Type-check without writing files |
| `npm run lint` | ESLint over `src/`, `test/` and `scripts/` |
| `npm run format:check` | Check formatting with Prettier |
| `npm test` | Build, then run the unit tests |
| `npm run test:integration` | Build, then run the tests that need the PlantUML runtime |
| `npm run test:coverage` | Unit tests with coverage thresholds |
| `npm run gallery` | Render every example into `artifacts/gallery/index.html` and run every layout check |
| `npm run check` | Everything a pull request must pass, in one command |

## Ways to contribute

### Report a bug

Open an issue with the bug template. The most useful thing you can attach is the
model JSON that shows the problem and the SVG or PNG you got, plus the output of
`diagramc --version`. Cut the model down as far as you can while the problem still
shows.

### Fix a layout defect

Add the model that shows the defect to `test/fixtures/regression/` as
`<kind>-<short-name>.json` first. `test/regression.test.mjs` runs every layout
check on every file there, so your fixture fails before the fix and passes after
it. If the defect was something a layout check should have caught but did not,
tighten the check in `src/qa/gates.ts` as part of the fix.

### Add or improve an example

Examples live in `examples/<kind>/`. Every kind has `minimal.json`, a realistic
example, a `notation.json` showcase where useful and `stress.json` (generated by
`scripts/generate-<kind>-stress.mjs`; edit the generator, not the output). The
tests render every file in `examples/` and run every layout check on it (for
sequence, timing and activity in the integration suite), so a new example is
tested as soon as it exists. Run `npm run gallery` and look at
the PNG before you open the pull request. Use invented, generic content (a web
shop, a library, a thermostat), never a real company's internal design.

### Add a notation feature to an existing kind

1. Extend the kind's schema (`src/kinds/<kind>/schema.ts`) and, if it has rules
   JSON Schema cannot express, its validator (`validate.ts`). Drawn strings must
   use the shared text definitions so they are checked and escaped.
2. Draw it (own engine: `layout.ts` and the shared shapes in `src/engine/`;
   PlantUML kinds: `to-plantuml.ts`).
3. Add a row to the notation checklist in `docs/kinds/<kind>.md`: the construct,
   its JSON, how UML 2.5.1 draws it, and the test that proves it.
4. Add positive and negative fixtures in `test/fixtures/<kind>/` and show the
   feature in `examples/<kind>/notation.json`.

### Add a diagram kind

Follow the recipe in [docs/kinds/README.md](docs/kinds/README.md): one folder in
`src/kinds/`, one line in `src/model/registry.ts`, a notation checklist, fixtures,
at least three examples and tests. Please open an issue first so we can agree on
the scope and the backend.

## Pull request checklist

- [ ] `npm run check` passes locally. If you touched a PlantUML kind, so does
      `npm run test:integration`.
- [ ] New behavior has tests; a layout fix has a regression fixture.
- [ ] Changed drawings were looked at (`npm run gallery`), not only tested.
- [ ] The notation checklist in `docs/kinds/<kind>.md` and the README are
      updated if user-facing behavior changed.
- [ ] No entry was added to `test/known-gate-failures.mjs`. That list only
      shrinks.
- [ ] Commit messages explain what changed and why, in plain sentences.

## How review works

The maintainer reviews every pull request, usually within a week. Expect
questions about notation (what UML 2.5.1 says), about layout on inputs nobody
tuned for, and about error messages, because agents read them. Small, focused
pull requests are reviewed fastest. Once the checks pass and the review is
resolved, the maintainer merges.

## Contributions written with AI agents are welcome

Many changes to this project are written with coding agents, and yours can be
too. One rule applies: **the human who opens the pull request is responsible for
it.** That means you:

- have read every line of the change and understand it;
- have run `npm run check` (and `npm run test:integration` for PlantUML kinds)
  and looked at the rendered diagrams the change affects;
- say in the pull request description which parts were written by an agent.

Agent output that no person has reviewed is not accepted. Please keep commit
messages and pull request descriptions free of tool-generated attribution lines
and session links; describe the change itself instead.

## Releases

The maintainer cuts releases by pushing a version tag; a workflow builds the
tarball and publishes the GitHub Release. The steps are in
[docs/releasing.md](docs/releasing.md).

## Code of conduct and security

Everyone taking part is expected to follow the [Code of Conduct](CODE_OF_CONDUCT.md).
Please report security problems privately as described in [SECURITY.md](SECURITY.md),
not in a public issue.
